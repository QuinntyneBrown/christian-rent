Accessibility

WCAG 2.2 level AA on every screen, by touch, by keyboard and with a screen reader.

WCAG 2.2 AA
  • Overview
  • Commitments
  • Focus
  • The component contract
  • Testing
  • Tokens

Overview

Accessibility is part of each component’s definition, not a pass at the end. Each component page states its role, its keys, its focus, its labels and its contrast.

Commitments

  • Text contrast is at least 4.5:1; large text, control edges and focus rings at least 3:1, in both themes.
  • Everything works with a keyboard alone, in an order that follows the screen, with a visible focus ring.
  • Every target is at least 44 × 44 px.
  • A state (verified, wanted, current, invalid) is carried by text or an attribute, never by colour alone.
  • Every field has a visible label and its error is tied to it.
  • Confirmations and errors are announced.
  • Reduced motion leaves nothing beyond a short fade.
  • At 200% text size nothing is lost or overlaps.
  • Each screen has one <h1>, one <main> and a skip link.
  • Photos have text alternatives that describe them.

The component contract

  • A state assistive technology must know is an attribute (aria-current, aria-invalid, aria-pressed, aria-busy, disabled) and the style hangs on that attribute.
  • Native elements first: a link is an <a>, a button a <button>, a choice a radio.
  • Dialogs come from the CDK.

Testing

  • Tab through every screen: order, visibility, no traps except a dialog.
  • Run the contrast check after any token change.
  • Read each screen with a screen reader: headings, landmarks, names, announcements.
  • Automated accessibility sweeps are kept in the e2e suite and run when a person asks.
