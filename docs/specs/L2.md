# L2 - Detailed Requirements

Each acceptance test names the L2 requirements it covers in a comment at its head
(`// Acceptance Test`, `// Traces to: L2-001, L2-003`, `// Description: ...`).

## L2-001: Browse shows approved listings
**Traces to:** L1-001

Browse is the home screen. It shows approved listings, newest first, to anyone, signed in or not.
A listing for rent shows as a card with its first photo, title, price and area; a wanted listing
shows as a card with no photo.

**Acceptance Criteria:**
1. Given approved listings exist, when anyone opens christian.rent, then Browse shows them newest first without asking them to sign in.
2. Given a listing is waiting in the review queue or has been removed, when anyone opens Browse, then that listing is not shown.
3. Given a listing for rent with photos, when its card is shown, then the card shows the first photo, the title, the price and the area.
4. Given a wanted listing, when its card is shown, then the card shows no photo and is labelled "Wanted" in text.
5. Given a card on Browse, when a person selects it, then the Listing screen for that listing opens.
6. Given no approved listing exists, when anyone opens Browse, then an empty state is shown with the two buttons that lead to posting.

---

## L2-002: Switch between Everything, For rent and Wanted
**Traces to:** L1-001

A switch on Browse limits the list to listings for rent, to wanted listings, or shows both.

**Acceptance Criteria:**
1. Given Browse is opened, when nothing has been chosen, then Everything is selected and both kinds of listing are shown.
2. Given Browse, when a person selects For rent, then only listings for rent are shown.
3. Given Browse, when a person selects Wanted, then only wanted listings are shown.
4. Given a search term is entered, when a person changes the switch, then the search term is kept and both apply together.
5. Given a choice on the switch, when the page is reloaded or its address is shared, then the same choice and search term are restored.

---

## L2-003: Search
**Traces to:** L1-001

The search bar finds approved listings by words in their title, note and area, without regard to
letter case or accents.

**Acceptance Criteria:**
1. Given approved listings titled "Parking space near church" and "Folding chairs", when a person searches "parking", then only the first is shown.
2. Given a listing whose note contains "gymnasium", when a person searches "GYMNASIUM", then that listing is shown.
3. Given a person is typing, when they pause for 300 ms, then the list updates without a page reload; an earlier search still in flight is cancelled and never replaces a later result.
4. Given a search term longer than 100 characters, when it is submitted, then only the first 100 characters are used.
5. Given a search term containing HTML or script, when the results are shown, then the term is rendered as text.

---

## L2-004: A search that finds nothing offers to post a request
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given a search that matches no approved listing, when the results are shown, then a no-results state names the search term and offers to post a wanted listing for it.
2. Given the no-results state, when a person takes the offer, then Post opens set to "I need", with the search term as the title.

---

## L2-005: Browse leads straight to posting
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given Browse, when it is shown, then it has two buttons: "I have something to rent" and "I'm looking for something".
2. Given Browse, when a person selects "I have something to rent", then Post opens set to "I have".
3. Given Browse, when a person selects "I'm looking for something", then Post opens set to "I need".

---

## L2-006: Browse loads in pages
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given more than 24 listings match, when Browse is opened, then the first 24 are shown and more load as the person reaches the end of the list.
2. Given the last page has loaded, when the person reaches the end, then no further request is made.
3. Given a page fails to load, when the failure happens, then the listings already shown stay, and a message with a "Try again" button is shown.

---

## L2-007: The Listing screen
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given an approved listing for rent, when anyone opens it, then it shows its photos, title, whether it is a space or a thing, price, when it is available, area and note.
2. Given an approved wanted listing, when anyone opens it, then it shows its title, whether it is a space or a thing, what the person will pay if given, when it is needed, area and note, and no photo.
3. Given a listing with several photos, when a person moves through them, then each photo can be reached by touch and by keyboard, and each has a text alternative.
4. Given a listing that is not approved, has been removed or does not exist, when anyone but its own poster or an admin opens its address, then a "not found" state is shown and nothing about the listing is revealed.
5. Given a listing, when it is shown, then its area is a city or neighbourhood and never a street address.

---

## L2-008: Who posted, and their church
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a listing, when it is shown, then it shows the name of the member who posted it and the name of their church.
2. Given the member is verified, when the listing is shown, then the member is marked "Verified" with text and an icon, not colour alone.
3. Given the church is verified, when the listing is shown, then the church is marked "Verified" in the same way, separately from the member.
4. Given the member or the church is not verified, when the listing is shown, then no verified mark is shown for it.
5. Given a listing, when it is shown to anyone, then the member's email address, phone number and street address are not shown and are not in the response.

---

## L2-009: Choose what is being posted
**Traces to:** L1-003

Post opens with one sentence, "I have / need a space / a thing to rent out", whose highlighted
words switch. "I have" makes a listing for rent; "I need" makes a wanted listing.

**Acceptance Criteria:**
1. Given Post, when a member switches "have" to "need", then the listing becomes a wanted listing, the sentence reads accordingly, and the photos field is removed.
2. Given Post, when a member switches between "a space" and "a thing", then the listing's kind changes and the fields already filled in are kept.
3. Given Post, when the highlighted words are used with a keyboard or a screen reader, then each is a control with a name and a state that says which choice is selected.
4. Given a person who is not a member, when they open Post, then they are asked to become a member or sign in, and are returned to Post afterwards with their choices kept.

---

## L2-010: The fields of a listing
**Traces to:** L1-003

A listing has a title, a price, when, an area, photos (for rent only) and a note.

**Acceptance Criteria:**
1. Given Post, when a member submits a title shorter than 3 or longer than 80 characters, then the listing is not posted and the title field says why.
2. Given a listing for rent, when a member submits no price, a negative price or a price above 100,000, then the listing is not posted and the price field says why; a price of 0 is accepted and shown as "Free".
3. Given a listing for rent, when a member sets the price, then they choose what it is per: hour, day, week or month.
4. Given a wanted listing, when a member leaves the price empty, then the listing is accepted and shows no price.
5. Given Post, when a member fills in "when", then they give either free text of up to 80 characters (for example "Weekday evenings") or a start and end date; an end date before the start date is refused.
6. Given Post, when a member submits no area, then the listing is not posted and the area field says why.
7. Given Post, when a member writes a note longer than 1,000 characters, then the listing is not posted and the note field says why; the note is optional.
8. Given invalid fields, when the member submits, then every invalid field is marked at once, focus moves to the first, and nothing the member typed is lost.
9. Given a request sent straight to the backend with invalid fields, when it is received, then the backend refuses it with the same rules.

---

## L2-011: Live preview
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given Post, when a member changes any field, then the preview card updates to show the listing as it will appear on Browse.
2. Given a wanted listing, when the preview is shown, then it is a card with no photo.
3. Given an empty field, when the preview is shown, then the card shows a placeholder in its place and never the word "undefined" or an empty price.

---

## L2-012: Posting and confirmation
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given valid fields, when a member submits, then the listing is saved as waiting for review, it enters the review queue, and a confirmation is shown.
2. Given a listing waiting for review, when the confirmation is shown, then it says truthfully that the listing will appear once it has been reviewed, and does not say it is already public.
3. Given the listing is approved, when anyone opens Browse, then the listing is shown.
4. Given a member selects the submit button twice, when both requests arrive, then one listing is created.
5. Given the request fails, when the failure happens, then the form keeps everything the member entered, including photos already added, and offers "Try again".
6. Given a member has posted 10 listings in 24 hours, when they post another, then it is refused with a message saying when they can post again.

---

## L2-013: Add photos to a listing for rent
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a listing for rent, when a member adds photos, then up to 6 are accepted, each shows a thumbnail, and the first is the one shown on the card.
2. Given photos have been added, when a member removes or reorders them, then the preview card follows.
3. Given 6 photos are added, when a member tries to add a seventh, then it is refused with a message.
4. Given a listing for rent with no photo, when it is posted, then it is accepted and its card shows a placeholder image.
5. Given a photo is uploading, when the member leaves Post, then the upload is cancelled and the photo is not kept.

---

## L2-014: Photos are checked before they are stored
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a file that is not a JPEG, PNG or WebP image by its content, when it is uploaded, then it is refused whatever its file name or declared type.
2. Given an image larger than 10 MB, or smaller than 400 × 300 px, or larger than 8,000 px on either side, when it is uploaded, then it is refused with a message naming the limit.
3. Given an accepted photo, when it is stored, then its location data and other embedded metadata are removed.
4. Given an accepted photo, when it is shown, then it is served from file storage at a size fitted to where it appears, and never from the database.
5. Given a photo belonging to a listing that is not approved, when anyone but its poster or an admin requests it, then it is not served.

---

## L2-015: Send a message about a listing
**Traces to:** L1-005

The Listing screen has a message box that sends a message to the person who posted.

**Acceptance Criteria:**
1. Given a member on an approved listing, when they write a message of 1 to 1,000 characters and send it, then the message is delivered to the person who posted and a confirmation replaces the message box.
2. Given a listing for rent, when the message box is shown, then it has start and end dates; given a wanted listing, then it has none.
3. Given dates are entered, when the end date is before the start date or the start date is in the past, then the message is not sent and the field says why.
4. Given an empty message or one over 1,000 characters, when the member sends it, then it is not sent and the field says why.
5. Given a person who is not a member, when they try to send a message, then they are asked to become a member or sign in, and their message and dates are kept for when they return.
6. Given a member's own listing, when they open it, then the message box is not offered, and a message sent to it straight to the backend is refused.
7. Given sending fails, when the failure happens, then the message text and dates are kept and "Try again" is offered.

---

## L2-016: A message is private to the two people
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a message, when it is delivered, then only the member who sent it and the member who posted the listing can read it.
2. Given a message is delivered, when the person who posted reads it, then they see the sender's name, church and verified marks, the listing it is about, the dates if any, and a way to reply.
3. Given a message, when it is sent, then neither person's email address or phone number is revealed to the other unless they write it themselves.
4. Given a member has sent 20 messages in an hour, when they send another, then it is refused with a message saying when they can send again.
5. Given a listing that has been removed, when a member tries to send a message about it, then it is refused.

---

## L2-017: Becoming a member
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given a person who is not a member, when they join, then they give their name and their church, and declare that they are a Christian; without all three they do not become a member.
2. Given a person joins, when they name their church, then they pick an existing church or enter a new one with its name and city.
3. Given a new member, when they join, then they enter the review queue as a new member and are not verified.
4. Given a member who is not yet verified, when they post or send a message, then they may, and their name is shown without a verified mark.
5. Given a person who is not a member, when they browse, search or read a listing, then they may; when they post, message or report, then the backend refuses until they are a member.
6. Given a name longer than 60 characters or a church name longer than 100, when it is submitted, then it is refused with the reason.

---

## L2-018: Verified members and churches
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given a new member in the review queue, when an admin approves them, then the member is verified and the mark appears on their listings.
2. Given a church entered by a member, when an admin confirms it, then the church is verified and the mark appears on the listings of all its members.
3. Given a member is verified and their church is not, when their listing is shown, then only the member is marked.
4. Given an admin removes a member, when the removal is made, then the member can no longer sign in, post or message, and their listings are no longer public.
5. Given anyone other than an admin, when they try to set a verified mark, then the backend refuses.

---

## L2-019: The review queue
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given an admin, when they open Admin, then the review queue lists new listings, reports and new members, oldest first, each labelled with its kind.
2. Given an admin selects an item, when it opens, then a detail panel shows everything needed to decide: for a listing, all its fields and photos and who posted it; for a report, the listing and the reason; for a new member, their name and church.
3. Given the queue is empty, when an admin opens Admin, then "All caught up" is shown.
4. Given more than 50 items wait, when an admin opens Admin, then they load in pages.
5. Given a person who is not an admin, when they open Admin's address or call its endpoints, then the backend refuses, no queue data is returned, and Admin's code is not loaded.

---

## L2-020: Approve, Keep or Remove
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a new listing, when an admin selects Approve, then it becomes public and leaves the queue; when they select Remove, then it never becomes public and leaves the queue.
2. Given a report, when an admin selects Keep, then the listing stays public and the report leaves the queue; when they select Remove, then the listing is no longer public and every open report on it leaves the queue.
3. Given a new member, when an admin selects Approve, then the member is verified; when they select Remove, then the member is removed as in L2-018.
4. Given Remove, when an admin selects it, then they are asked to confirm before it takes effect.
5. Given two admins act on the same item, when the second decision arrives, then it is refused with a message that the item was already decided, and the first decision stands.
6. Given any decision, when it is made, then who made it, on what and when is recorded.
7. Given a listing is removed, when the removal is made, then the member who posted it is told that it was removed.

---

## L2-021: Report a listing
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a member on a listing, when they select Report, then they choose a reason from a fixed list (not a real listing, inappropriate, a scam, something else) and may add a note of up to 500 characters.
2. Given a report is sent, when it is received, then it enters the review queue and the member sees a confirmation.
3. Given a member has already reported a listing, when they report it again, then no second report is created.
4. Given a report, when it is shown to anyone, then the member who posted the listing is never told who reported it.
5. Given a person who is not a member, when they try to report, then they are asked to become a member or sign in.

---

## L2-022: CAD, km and Canadian spelling
**Traces to:** L1-009

**Acceptance Criteria:**
1. Given a price, when it is shown, then it is in Canadian dollars with its period, for example "$25 / day", with cents shown only when they are not zero.
2. Given a distance, when it is shown, then it is in kilometres, for example "4 km".
3. Given a date, when it is shown, then the month is written as a word, for example "Dec 3, 2026", so that it cannot be misread.
4. Given any text the product writes, when it is shown, then it uses Canadian spelling, for example "neighbourhood" and "colour".
5. Given an area, when a member enters it, then it is a place in Canada.

---

## L2-023: The wordmark
**Traces to:** L1-009

**Acceptance Criteria:**
1. Given any screen, when it is shown, then the wordmark reads "christian.rent" in lowercase and is never written "Christian Rent" or "ChristianRent".

---

## L2-024: Nothing beyond renting
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given any screen, when it is shown, then it offers no way to pay, to take a deposit or to enter a card.
2. Given a listing, when it is shown, then it shows no booking calendar, no review, no rating and no advert; "when" is a description, not a reservation.
3. Given a message with dates is sent, when it is delivered, then the listing's availability does not change and nothing is reserved.

---

## L2-025: The backend decides what is allowed
**Traces to:** L1-011

**Acceptance Criteria:**
1. Given any endpoint other than browsing, searching and reading an approved listing, when it is called without a signed-in member, then it responds 401.
2. Given a member, when they request a listing, message or photo that is not theirs to see, or try to change one that is not theirs, then the backend refuses and reveals nothing about it.
3. Given a control is hidden in the frontend, when the same action is sent straight to the backend by someone not allowed, then it is refused.
4. Given a refusal a screen must branch on, when it is returned, then it is a ProblemDetails with a `code`, and the member sees a generic message.

---

## L2-026: What a member writes is data
**Traces to:** L1-011

**Acceptance Criteria:**
1. Given a title, note, message, member name or church name containing HTML or script, when it is shown anywhere, then it is rendered as text and nothing runs.
2. Given any input, when it reaches the backend, then it is validated for type, length and range before it is used, and database access is parameterised.
3. Given a response, when it is sent, then it carries a Content-Security-Policy that allows no inline script and no third-party script.

---

## L2-027: Transport, sessions and abuse
**Traces to:** L1-011

**Acceptance Criteria:**
1. Given a request over HTTP, when it is received, then it is redirected to HTTPS, and responses carry HSTS.
2. Given a request that changes data, when it comes from another site, then it is refused.
3. Given one client makes more than 120 read requests or 30 write requests in a minute, when the next arrives, then it is refused with 429 and a Retry-After header.
4. Given a secret (a key, a connection string, a token), when the system is deployed, then it comes from configuration outside the repository.

---

## L2-028: Personal data is kept to a minimum
**Traces to:** L1-011

**Acceptance Criteria:**
1. Given a member, when they join, then only what the product uses is collected: their name, their church and what is needed to sign in and reach them.
2. Given a member asks to leave, when their membership is deleted, then their listings and photos are no longer public and their personal data is deleted or made anonymous within 30 days.
3. Given a log, metric or trace, when it is written, then it holds no contact detail, token, message text, query string or request body, and a route is recorded as its template.

---

## L2-029: Fast on a phone
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given a mid-range phone on a 4G connection, when Browse is opened for the first time, then the largest content is painted within 2.5 s and layout shift stays under 0.1.
2. Given Browse is opened, when its code loads, then the code for Listing, Post and Admin is not in the initial download.
3. Given a card's photo, when it is shown, then it is sized to the card, has its space reserved before it loads, and loads lazily when below the fold.
4. Given a person interacts with any control, when they do, then the screen responds within 200 ms.

---

## L2-030: Fast and bounded on the backend
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given 10,000 approved listings, when a page of Browse or a search is requested, then the backend responds within 300 ms at the 95th percentile.
2. Given one listing is requested, when it is read, then the backend responds within 200 ms at the 95th percentile.
3. Given any list endpoint, when it is called, then it returns at most one page, and a page size above 50 is refused.
4. Given a person scrolls 500 listings on Browse, when they continue, then memory in the browser stays bounded: listings far off screen are released.

---

## L2-031: Every screen at every width
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given a viewport from 320 px wide, when any screen is shown, then nothing is cut off and the page does not scroll sideways.
2. Given a viewport under 576 px, when Browse is shown, then cards are in one column; from 576 px, 768 px, 992 px and 1200 px the number of columns grows as the mocks draw it.
3. Given a viewport under 768 px, when Listing is shown, then the message box is below the listing; from 768 px it is to the right of it.
4. Given a viewport under 768 px, when Post is shown, then the live preview is below the form; from 768 px it is beside it.
5. Given a viewport under 768 px, when Admin is shown, then only the queue is shown; from 768 px the detail panel and its Approve, Keep and Remove buttons are beside the queue.
6. Given any viewport, when a control is shown, then its touch target is at least 44 × 44 px.

---

## L2-032: Accessible to everyone
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given any screen, when it is checked, then it meets WCAG 2.2 level AA, including a contrast of at least 4.5:1 for text.
2. Given any action, when it is done with a keyboard alone, then it can be completed, focus is always visible and its order follows the screen.
3. Given a state (verified, wanted, selected, invalid), when it is shown, then it is carried by text or an attribute a screen reader announces, never by colour alone.
4. Given a confirmation or an error appears, when it does, then a screen reader announces it.
5. Given a form field, when it is shown, then it has a visible label, and its error is tied to it.
6. Given a person who asks for reduced motion, when a screen changes, then nothing animates beyond a short fade.
7. Given text is enlarged to 200%, when any screen is shown, then nothing is lost or overlaps.

---

## L2-033: Failing clearly
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given a request is in flight, when a screen waits for it, then a loading state is shown in the shape of what will arrive.
2. Given the backend cannot be reached, when a screen needs it, then a plain message and "Try again" are shown, and no technical detail.
3. Given an address that matches no screen, when it is opened, then a "not found" screen with a way back to Browse is shown.
4. Given an unhandled error on the backend, when it happens, then the response is a ProblemDetails with no stack trace, and the error is recorded with a trace id.

---

## L2-034: Operable in production
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given the backend is running, when its health endpoint is called, then it reports whether it is alive and whether it can reach its database and file storage.
2. Given any request, when it is handled, then a trace, its duration and its outcome are emitted through OpenTelemetry.
3. Given the database schema changes, when the system is deployed, then the change is applied by a command, and never by the API as it starts.
4. Given the data, when a day passes, then a backup exists from which listings, members, messages and photos can be restored.
